# 제품 기획

기준일: 2026-10-13. 개인 운영 기록을 제외한 공개 기획입니다. 구현 상태는
[검증 기록](verification.md), 수치 계산은 [비중 규칙](allocation.md)을 참고합니다.

## 목표

한 사람의 계좌를 사전에 정한 정책 안에서 지속 운용하고, 아이폰 앱으로 판단 이유와 결과를 보고합니다.
사용자는 운용 범위·한도·중지 여부와 투자논리를 정합니다. 최종 제품은 정책 안의 거래마다 승인을 요청하지
않는 구조를 목표로 합니다. 현재는 계좌 조회·판단 기록·보고와 지시 이력을 제공합니다.
내장 가상계좌는 제거했으며 매니저의 자동 주문 실행은 연결하지 않았습니다.

```text
계좌·시장 감시 → 운용 판단 → 목표 비중·수량 → 타점 감시
→ 독립 위험 검증 → 주문·체결 확인 → 보고 → 재평가
```

## 설계 원칙

1. 위험한 동작은 검증 코드가 차단하며 판단 계층이 이를 우회할 수 없습니다.
2. 총 주식 비중 상한은 결정론적 코드가 정합니다. LLM은 종목 구성을 조언하고 상한 이하로 축소만 제안합니다.
3. 시세·계좌·주문 상태가 불명이면 위험 확대를 차단하고 조회·대사를 우선합니다.
4. 주문 요청과 체결을 구분하며 응답 유실을 새 주문의 근거로 해석하지 않습니다.
5. 운용 중지는 강제 청산이 아닙니다. 기존 주문 확인과 대사는 계속합니다.
6. 정책은 버전과 변경 이력을 갖고 사용자만 한도를 바꿉니다. 외부 뉴스는 명령이 아닌 데이터입니다.

## 조직과 권한

| 역할 | 책임 | 구현 방향 |
| --- | --- | --- |
| 리서치 | 투자논리 점검·틸트·이벤트·아이디어 | `mind` thesis·judge, advisor 예정 |
| 자산운용 | 투자북 목표 비중·종목 구성 | `core/allocation.py` 계산 함수 구현, 주문 연결 예정 |
| 트레이딩 데스크 | 할당 자본 내 전략별 진입·청산 | 전략 인터페이스·장부 분리 예정 |
| 리스크관리 | 계좌·장부·전략·종목·주문 한도 | `guard.py`·`policy/v1.toml` 판정·경보 구현, 주문 경로 연결 예정 |
| 주문 실행 | 승인된 의도 제출·취소·정정·결과 조회 | 브로커 개별 Gateway 구현, 매니저 자동 주문 연결 예정 |
| 백오피스 | 체결·비용·원장·장부별 NAV·대사 | 원장 기반 구현, 실계좌 통합 회계 예정 |
| 앱·보고 | 사용자 지시 접수·조회·알림 | SwiftUI·SSH·CLI·아웃박스 |

프론트 역할은 주문 의도만 만들고, 리스크 검증을 통과한 의도만 실행합니다.
사용자의 증권사 앱 수동 주문은 동기화 대상으로 관리합니다.

## 자금과 전략

투자북 80~90%, 트레이딩북 10~20%(시작 10%)의 내부 장부 분리를 제안합니다.
이는 미검증 정책 초안이며 실제 자금 할당은 하지 않습니다. 각 장부는 입출금 보정 단위 NAV와
전략별 포지션을 기록하고 계좌 리스크는 합산합니다. 장부 할당과 주식 비중은 다른 개념입니다.
투자북·트레이딩북·수동 포지션을 합산한 계좌 노출에 가장 엄격한 한도를 적용하는 구조를 목표로 합니다.

투자북은 주간 비중 계산과 5%p 조정 밴드, 2거래일 안의 조정을 사용합니다.
트레이딩북은 `pullback` → `pead` → `breakout` → `llm-idea` 순으로 검증합니다.
전략은 백테스트 → 브로커 검증 환경(지원 시) → 별도 결정한 소액 실전 → 정식 할당의 검증 단계를 목표로 합니다.
내장 가상계좌의 가정 체결로 성과를 계산하는 기능은 제공하지 않습니다.

| 트레이딩북 한도 초안 | 기준 |
| --- | --- |
| 진입가·손절가 기준 거래당 계획 손실 | 트레이딩북 NAV의 1% |
| 전략별 하루 손실 | 트레이딩북 기준 −2%에 해당 전략 정지 |
| 전체 하루 손실 | 트레이딩북 기준 −3%에 데스크 정지 |
| 전략별 월 손실 | 트레이딩북 기준 −6%에 전략 정지 |
| 고점 대비 손실 | 트레이딩북 기준 −15%에 데스크 정지 |

손절 가격으로 계산한 계획 손실은 갭·체결 지연에 따른 실제 손실 상한을 보장하지 않습니다.
장중 급락은 알림을 보내며, 계좌 낙폭 비상 정지·데이터 불명 차단·전략 손실 정지는 별도 규칙입니다.

## 판단·실행·보고 계약

판단에는 ID, 정책 버전, 데이터 시각, 근거·대안·불확실성, 목표·만료·무효화 조건을 기록합니다.
투자논리 카드는 버전별 사용자 승인 후 효력을 갖습니다. `broken`은 승인된 자동 무효화 조건의 인용이 필요합니다.
실행 직전에 잔고·미체결·시세·정책을 다시 검증하며 결과 불명 주문은 대사 전 중복 실행하지 않습니다.

서버가 보고 원본을 먼저 저장합니다. 앱·CLI·HTML·Markdown은 같은 보고 ID를 표현합니다.
정기·체결·위험·예외 보고를 제공하며, 원격 푸시에는 일반 문구와 보고 참조만 넣습니다.
앱·SSH 연결이 끊겨도 서버 워커와 기록은 유지됩니다.

## 개발 순서

| 순서 | 할 일 | 완료 기준 |
| --- | --- | --- |
| 기반 | 결과 불명 주문의 재제출 차단·조회 복구 | 구현·단위 테스트 기반 있음 |
| 1 | 모든 주문 경로의 guard·버전 정책·알림 통합 | 판정·정책·경보 구현(2026-10-14), 주문 경로·실제 입력 연결 남음 |
| 2 | 실계좌 현금·입출금·결제·미체결과 장부 원장 | 잔고 대사, 입출금만으로 성과 불변 |
| 3 | 카드·판단 → 목표 수량 → 주문 의도 | 계산 parity, 계획 충돌·만료 처리 |
| 4 | advisor 계약과 뉴스·실적 출처 | 스키마·만료 검증, 근거 없는 수치 차단 |
| 5 | 전략별 백테스트·데이터 검증 | 비용·지연 가정과 표본 외 검증 |
| 6 | 브로커 검증 환경 연동·장애 시나리오 시험 | 리스크 위반·중복 주문 차단, 판단부터 보고까지 추적 |
| 7 | 제한된 실전 어댑터 | 계좌·금액·정책 확정과 별도 전환 결정 |

실전 전환은 과거 성과만으로 자동 결정하지 않습니다. 자동매매의 운영 안정성과 투자 성과는 각각 검증합니다.
